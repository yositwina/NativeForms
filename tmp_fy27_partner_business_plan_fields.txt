TwinaForms predominantly uses custom objects included in the managed package. These objects store form projects, forms, versions, form elements, actions, publications, themes, package configuration, and submission-log encryption metadata.
The app can also interact with standard or custom Salesforce objects selected by the customer when they configure prefill or submit actions, such as Contact, Lead, Account, Case, Campaign Member, or other customer-selected objects. Those interactions are configuration-driven and respect Salesforce permissions and validation.

--- Text56
TwinaForms uses secure API connections between Salesforce and TwinaForms AWS services.
The Salesforce managed package calls AWS endpoints over HTTPS for tenant setup, publishing, public form runtime support, prefill, submit processing, and submission-log services. Protected Salesforce-to-AWS calls are authenticated with Bootstrap V2 HMAC request signing. The signing secret is generated in Salesforce, stored in protected package-controlled configuration, and used server-side by Apex. Requests include org id, timestamp, nonce, body hash, and HMAC-SHA256 signature.
AWS connects back to Salesforce only after an authorized admin completes OAuth using the packaged Salesforce External Client App. TwinaForms stores tenant connection data server-side and validates org identity. AWS API operations are scoped by org id and tenant status. Salesforce object and field operations are based on customer configuration, use allowlisted metadata, and avoid arbitrary unauthenticated access.
TwinaForms follows Salesforce Connected App / External Client App compliance requirements. OAuth credentials are not exposed in the browser, refresh tokens are stored server-side, and package UI users do not handle client secrets.
